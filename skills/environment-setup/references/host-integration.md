# Host integration

Change host instructions only within the user's request. Preserve existing authority, unrelated sections, tool restrictions and explicit choices. Installing skills does not authorize rewriting a global AGENTS.md or CLAUDE.md.

A host entry should carry the behaviors needed even before a skill is loaded. Adapt these responsibilities to existing instructions rather than copying the workflow catalog:

- Use the installed Harness skill whose stated responsibility covers the requested outcome or a distinct necessary operation, without requiring the user to name it. Read its current instructions unless already available in context. Select by responsibility, not individual commands; suboperations fully covered by an active skill do not trigger a redundant chain. Report unavailable required skills and continue independent work.
- Completing a skill's responsibility returns to the broader authorized objective. Planning-only work remains planning-only; planning within authorized implementation returns to implementation. Skill defaults do not revoke existing authorization or create extra approval steps.
- When starting substantive project work with unknown context, locate the existing environment and inspect its short map; with a supplied continuation entry, start there. Follow relevant references and reuse current context. Isolated questions and mechanical edits with sufficient context need no discovery. Do not initialize storage merely to look for it.
- Preserve useful decisions, investigation and continuation when losing the conversation would cause meaningful loss. Reading context does not require a work record; short collaborations do not automatically require team/front files. Keep one canonical source and report failed or uncertain saves.
- Code and developer documentation must make sense without the agents' execution plan. Keep internal assignments and handoffs in the external environment. Close temporary work only after the whole objective is complete, active consumers are resolved and retained deliverables are preserved.
- Apply the user's delegation, model, effort, cost, testing and QA policies and the project's requirements. Distinguish running existing checks, writing tests and performing flow QA. Reuse valid evidence; do not add verification loops without a concrete reason. Keep personal testing preferences in the user's instructions and project-specific commands in repository guidance.
- Feature implementation does not itself authorize commit, push, PR, merge, release or deployment. Existing authorization persists for its scope.

The environment README contains its map and project-specific guidance. Skills define process responsibilities and outputs. Saved permissions and status are context, not independent authority or proof of current execution. Mandatory skill use is a behavioral instruction; it cannot guarantee universal selection by every model. Check availability, loading or valid reuse, application and composition in the actual host when evaluating behavior. Do not add lifecycle hooks, automatic memory injection, prompt transcripts or a mandatory invocation announcement.

Use the host's real capabilities for agents, IDs, worktree operations and permissions. Under the local storage contract, a worktree tool must be able to honor `<environment>/worktrees/<name>` before creation; a tool preference does not change the required destination. Do not invent parameters or silently substitute models. Persist concrete team settings in the work's temporary `team.md` only when useful for coordination or continuation.

When replacing earlier tooling, identify active consumers before removing discovery entries or helper paths. Preserve legacy knowledge and continuations separately; Harness does not read or migrate old state implicitly. Validate the newly installed inventory in a fresh host session before declaring the replacement effective.
