# Behavior validation

Mechanical tests establish helper and packaging guarantees. Evaluating skills requires observing an agent handle a realistic request in the actual host; reading the instructions for consistency does not establish automatic selection.

## Setup and evidence

Use an isolated workspace with only the raw artifacts needed for the request and an authorized host configuration. Test installed skills with the intended global integration instructions. Do not replace personal configuration for an evaluation without authorization. Record host, model/effort, skill version, instruction version and any configuration difference; do not invent settings the host does not expose.

Independent agents and paid evaluation sessions require their corresponding authorization. Give an evaluator the natural request and raw artifacts, not expected decisions, suspected defects or the author's conclusions. An explicit `$skill-name` prompt tests application, not implicit selection.

Observe these separately using existing host tool/file-access evidence:

- Availability: the skill appeared in the inventory supplied to the agent.
- Selection and loading: its current instructions were read or demonstrably already present. An announcement alone is insufficient.
- Application: actions and results followed the requested responsibility, relevant project constraints and authorization.
- Composition: necessary suboperations returned to the broader objective without redundant workflows or records.

Record concise findings and evidence references, not transcripts or reasoning traces. Mark unavailable evidence as unverified. A missing installation differs from a selection failure; valid instruction reuse differs from skipped loading.

## Representative cases

Select cases affected by the change rather than running a fixed campaign after every edit.

| Request and setup | Observe |
| --- | --- |
| Narrow code fix with known context | Implementation and relevant verification without unrelated planning or records |
| Focused documentation edit | Documentation responsibility and affected-reference checks without another project survey |
| Planning-only request, then separately an implementation requiring planning | A plan alone grants no execution authority; a planning suboperation does not stop authorized implementation |
| Isolated checkout with a new branch | One worktree operation can cover branch setup; existing changes and host constraints are respected |
| New project session with a map linking an applicable product constraint | Relevant unknown guidance is discovered without loading all knowledge or forcing a work record |
| Explicitly authorized short collaboration | Native messages/results can suffice without team/front files |
| Completed work containing a retained original HTML output | Contents and durable reference are preserved before cleanup; originals are not presumed regenerable |
| Cosmetic adjustment under a policy reserving aesthetic review for the user | No new cosmetic tests or agent-run visual QA solely because a visual detail changed |
| Persistence behavior under a real-test-database policy | Representative observable results and persisted effects, not mocked persistence or per-function coverage by default |
| General discussion of product direction | No forced code-defect review or unrequested implementation |

Also inspect boundaries for commit, PR and integration responsibilities when affected. Judge discovery, preservation and composition rather than catalog coverage: a small fix that loads no skill can be the correct behavior. Use disposable local or read-only setups rather than publishing a real PR for a test. Review-only work stays read-only; stored permission notes do not grant new authority. Relevant coordinator checks may resolve concrete gaps without routinely repeating worker verification.

## Completion and limits

Use a fresh session when evaluating discovery. If an intermittent failure is already known, predeclare a small number of fresh-session attempts in the same configuration and record each result; do not stop after the first success. Repeat affected cases after a correction. Broaden only for changed behavior, failures or a concrete unresolved concern.

Report mechanical, installation and behavioral results separately. Successful local cases do not establish universal invocation or a reliability percentage. If selection remains inconsistent despite availability and clear responsibility, retain that limitation rather than adding lifecycle hooks, a dispatcher or production telemetry as an unrequested fix. Remote behavior can only be validated once the actual service and authorized access exist.
